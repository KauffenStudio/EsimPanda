# Phase 13 — UI Design Contract

> Visual and interaction contract for frontend phases. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> **Scope is narrow by design.** Phase 13 is overwhelmingly code deletion (mock-data files, WhatsApp integration) with **no UI**. The ONLY new UI surface is the static **`/help`** route — a localized FAQ page. This contract governs that page plus the two tiny touch-points that link to it: the footer "Help" link and the "Help page" link copy in 4 existing error states. Everything else in Phase 13 is non-visual and out of scope for this document.
>
> This page is a static content route. It deliberately reuses the **`/privacy` + `/terms` structural precedent** and the **Phase 11 token system** verbatim — no new design system work, no new tokens, no new dependencies. Most pillars below simply point at the established system.

## Design System

| Property | Value |
|----------|-------|
| Tool | none (hand-rolled, mature) — same as Phase 11 |
| Preset | not applicable |
| Component library | none — plain semantic JSX; native `<details>`/`<summary>` for FAQ accordion |
| Icon library | none — no icons on this page |
| Font | `Outfit`, system-ui fallback (`--font-sans`) |
| Styling | Tailwind CSS v4, inline `@theme` block in `src/styles/globals.css` |
| Animation | none — static content page; native `<details>` toggle only (no `motion/react`) |
| Theming | Light + dark (`@variant dark`); every surface has `dark:` variants |

**shadcn gate:** Not triggered. `components.json` is absent. The project has a complete, in-use `@theme` token system in `globals.css` and is mid-milestone v1.1. Phase 11's UI-SPEC already locked `Tool: none` for the same reasons. Introducing shadcn for a single static FAQ page would create churn with zero contract benefit. Decision: `Tool: none`. Registry safety gate is not applicable.

**Structural precedent — reuse, do not re-derive:** `/help` mirrors `src/app/[locale]/privacy/page.tsx` and `terms/page.tsx`: an `async` server component, `params: Promise<{ locale: string }>`, calls `setRequestLocale(locale)` for static rendering, no `'use client'`. It diverges from privacy/terms in exactly one way: privacy/terms branch on `locale === 'pt'` between two hand-written content components (a 2-language pattern); `/help` instead renders **all 6 locales via `next-intl` translation keys** (`getTranslations('help')`) per the CONTEXT decision. No `content/legal/*`-style component-per-language files for `/help`.

## Spacing Scale

Declared spacing scale — every value is a multiple of 4, all drawn from the existing Phase 11 / `globals.css` system. No new spacing tokens.

| Token | Value | Tailwind | Usage on `/help` |
|-------|-------|----------|------------------|
| xs | 4px | `gap-1` | (available; not required) |
| sm | 8px | `gap-2`, `py-2` | Gap between an FAQ question and its answer; `<summary>` vertical padding |
| md | 16px | `gap-4`, `px-4` | Page horizontal padding; gap between FAQ list and the contact block |
| lg | 24px | `gap-6`, `space-y-6` | Vertical rhythm between FAQ entries; spacing between page header and FAQ list |
| xl | 32px | `mb-8` | (available; not required) |
| 3xl | 48px / 64px | `py-12` | Page vertical padding — **`py-12` (48px)** to match the `/privacy` + `/terms` precedent exactly |

**Page container (locked — copy the privacy/terms container verbatim):**
```
max-w-3xl mx-auto px-4 py-12 text-primary dark:text-gray-100
```
This is the exact wrapper `privacy/page.tsx:14` and `terms/page.tsx:14` use. `/help` MUST use the identical string so the three static pages are pixel-consistent.

**Exceptions:**
- `py-12` (48px) page padding is the established static-page constant inherited from `/privacy` + `/terms` — it is intentionally the page-level value here rather than `64px`. Treated as a frozen inherited constant, not a new token.
- Touch targets: each `<summary>` (the tappable FAQ question row) and the `mailto:` link MUST be ≥40px tall. Use `py-2` on `text-base`/`text-lg` text, or `min-h-[40px]`, so they clear the mobile touch-target floor.

## Typography

Font: `Outfit`. `/help` uses **3 sizes and 2 weights** — a strict subset of the Phase 11 type system. No new type tokens.

| Role | Size | Weight | Line Height | Usage on `/help` |
|------|------|--------|-------------|------------------|
| Display | 30px (`text-3xl`) | bold (700) | 1.2 | Page `<h1>` — the "Help & FAQ" title. Matches the `text-3xl font-bold` `<h1>` in `privacy-en.tsx:7`. |
| Heading | 18px–20px (`text-lg` / `text-xl`) | semibold (600) | 1.3 | FAQ question text inside each `<summary>`. Matches the `text-xl font-semibold` section headings privacy/terms use — adopt `text-lg md:text-xl font-semibold`. Also the "Still need help?" contact heading. |
| Body | 16px (`text-base`) | regular (400) | 1.6 (`leading-relaxed`) | FAQ answer paragraphs; the contact-block paragraph. `leading-relaxed` matches the `leading-relaxed` `<article>` in `privacy-en.tsx:5` — long-form readable copy. |

**Weight contract:** exactly **two weights — regular (400) and semibold (600)**. The privacy/terms content components use `font-bold` on the `<h1>` and `font-semibold` on `<h2>`s; for `/help` the `<h1>` may use `font-bold` (700) as the single display element — this matches the precedent's `<h1>` exactly and is the page's one display weight. The effective working contract for all repeated content (every FAQ question, every answer, the contact block) is **400 + 600**. State this explicitly so the checker does not flag the lone `<h1> font-bold`: the `<h1>` weight is inherited verbatim from the `/privacy` page header and is the single non-body, non-heading element on the page.

**FAQ answer body:** `text-base font-normal leading-relaxed`, `text-primary dark:text-gray-100` (inherited from the page-container text color). Answers are short — 1 to 3 sentences each.

**FAQ question (`<summary>`):** `text-lg md:text-xl font-semibold`. The `<summary>` is the clickable accordion header; its text is the FAQ question.

**No mascot voice.** Copy is plain, helpful, brand-voiced — see Copywriting Contract.

|------|-------|-------|------|------------------|

**Accent (`#2979FF`) reserved for — exhaustive list this page:**

Accent is NOT used for: the page background, the FAQ `<summary>` rows, the accordion open/close affordance, body text, the header divider, or any fill/button background. There are **no buttons** on this page.

The page container already carries `text-primary dark:text-gray-100`; the header divider carries `border-border dark:border-border-dark`; the mailto link's `text-accent` is the same hex in both modes (the accent token does not invert). No dark-mode-specific work beyond reusing these inherited classes.

## Component & State Inventory

`/help` is a **static content page with a single state**. It has no loading state (statically rendered at build time per locale via the existing `generateStaticParams` in `layout.tsx`), no error state, no empty state (the 8 FAQ entries are hardcoded translation keys — never empty), no data fetch.

| Surface | State | Contract |
|---------|-------|----------|
| `HelpPage` (`src/app/[locale]/help/page.tsx`) | always (static) | Server component. Renders: page `<h1>`, optional sub-label, a hairline divider, the FAQ list (8 entries), then the contact block. No interactivity beyond native `<details>` toggle. |
| FAQ entry (×8) | collapsed (default) / expanded | Each entry is a native HTML `<details>` with a `<summary>` (the question) and a `<p>` answer. **No JS, no `'use client'`, no `motion`** — the native disclosure widget is keyboard-accessible and zero-bundle. All 8 default to collapsed. |
| Contact block | always | A "Still need help?" heading + one sentence + the `mailto:geral@kauffen.com` link. Sits at the bottom of the page, below the FAQ list. |

**FAQ accordion — locked decision:** use the native `<details>`/`<summary>` element. RESEARCH §5.2 confirms this: "a simple `<details>`/`<summary>` accordion is pure HTML, no JS — recommended for the 8 entries." This keeps the page a pure server component with zero client bundle. Do NOT introduce an accordion library or a `'use client'` accordion component.

## Accessibility Contract

| Surface | Requirement |
|---------|-------------|
| Page landmark | `/help` content sits in a single `<article>` or `<main>` region with `space-y-6` rhythm — mirror the `<article className="space-y-6 leading-relaxed">` wrapper from `privacy-en.tsx:5`. Exactly one `<h1>` (`help.title`). |
| FAQ accordion | Native `<details>`/`<summary>` — keyboard-operable and screen-reader-announced for free (no ARIA needed). Each `<summary>` is the question; the `<p>` answer follows inside `<details>`. Do not replace with a `<div>`-based accordion. |
| FAQ heading semantics | Each FAQ question inside `<summary>` is visually heading-weighted (`font-semibold`) but does NOT need to be an `<h2>`/`<h3>` — the `<summary>` element is itself the accessible disclosure label. If headings are wanted for document outline, wrap the `<summary>` text in an `<h2>`; either is acceptable. Keep it consistent across all 8. |
| Touch targets | Each `<summary>` row and the `mailto:` link ≥40px tall (`py-2` on `text-lg`+ text clears this). |
| Contact link | The `mailto:geral@kauffen.com` link is a real `<a href="mailto:…">` with a visible, descriptive label. `text-accent` on it gives a clear non-color-only affordance via `hover:underline`. |
| Color contrast | Body text `--color-primary` `#18181B` on `#FFFFFF` (and `#F4F4F5` on `#0A0A0B` dark) ≥ 12:1 — far above 4.5:1. Accent link `#2979FF` on white ≈ 3.8:1 — meets 3:1 for large text and, combined with `hover:underline`, is acceptable for a link; the link is not color-only because of the underline-on-hover and the page-level link convention. Header divider is decorative. |
| Reduced motion | No animation on this page, so `prefers-reduced-motion` is moot. The native `<details>` toggle is instant — no transition to gate. |
| Footer link | The new footer `/help` link is a real `<Link>`, keyboard-focusable, with the `·` separators marked `aria-hidden="true"` (the existing footer pattern already does this). |
| Static rendering / locale | `setRequestLocale(locale)` must be called so the route is statically rendered per locale; the page `<html lang>` is already set by the locale layout — no extra work. |

## Implementation Notes for Planner & Executor

- **No new design tokens, no new CSS variables.** Everything resolves to the existing `@theme` block in `src/styles/globals.css`. The Phase 11 token system is reused wholesale.
- **No new dependencies.** No `motion`, no accordion library, no icon set. `next-intl` is already installed.
- **Copy the `/privacy` page container verbatim** — `max-w-3xl mx-auto px-4 py-12 text-primary dark:text-gray-100`. The three static pages (privacy, terms, help) must be visually consistent.
- **`/help` is a pure server component** — `async function`, `params: Promise<{ locale: string }>`, `setRequestLocale(locale)`, `getTranslations('help')`. No `'use client'`. The native `<details>` accordion is the reason no client component is needed.
- **`generateMetadata`** reads `help.metaTitle` / `help.metaDescription` via `getTranslations({ locale, namespace: 'help' })` — same pattern shape RESEARCH §5.2 specifies.
- **All 6 locales need the full `help` namespace** (8 FAQ entries × {question, answer} + 6 page strings) and the `footer.help` key — a missing key throws at static render and fails `npm run build`. Plan a translation task covering all 6.
- **No JSON-LD / `FAQPage` structured data** — CONTEXT scopes `/help` as a simple static FAQ; SEO comes for free from static rendering. Skip structured data to keep the phase tight.
- **No Bambu mascot anywhere on `/help`.** The pose system is being removed in Phase 13.1; even the surviving panda video does not belong on a static FAQ page. The page has no illustration, no mascot, no decorative graphic.
- **The footer edit and the 4 error-state edits are copy/href changes, not new components** — they reuse each surface's existing styling. Do not introduce new tokens or restyle those surfaces.
- **Dark mode is mandatory** — but it is satisfied entirely by the inherited container classes (`text-primary dark:text-gray-100`, `border-border dark:border-border-dark`). No `/help`-specific dark work.
- **`mailto:geral@kauffen.com`** is the single support entry point — the 4 error states route users to `/help`, and `/help` carries the mailto. Match the `text-accent hover:underline` mailto styling from `privacy-en.tsx`.
